# Feature Specification: Autonomous Cleaning

**Feature Branch**: `003-autonomous-cleaning`  
**Created**: 2026-03-21  
**Status**: Draft  
**Input**: User description: "自動走行での掃除をする機能。"

## Clarifications

### Session 2026-03-21

- Q: 清掃範囲は毎回どこまでにするか？ → A: 地図上の到達可能な全床面のみ。
- Q: 清掃中に低バッテリーになった場合はどうするか？ → A: ドック復帰を試み、失敗したら停止する。
- Q: 清掃開始可否と低バッテリー判定の閾値は？ → A: 開始可否はバッテリー残量30%以上、低バッテリー判定は20%未満。
- Q: e-stopの停止応答閾値は？ → A: 50ms以内（1制御周期以内）。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 既知の部屋を自動で掃除する (Priority: P1)

利用者として、手動操作をしなくてもロボットに部屋全体の掃除を任せたい。これにより、事前に把握済みの室内を効率よく清掃できる。

**Why this priority**: 本機能の中心価値そのものであり、自動走行で清掃を完遂できなければこの機能は成立しないため。

**Independent Test**: 利用可能な地図と現在位置がある状態で自動清掃を開始し、ロボットが到達可能な床面を順次清掃して完了状態になることを確認すれば、このストーリー単体で価値を検証できる。

**Acceptance Scenarios**:

1. **Given** ロボットが待機状態で、清掃対象となる室内地図と現在位置が利用可能、**When** 利用者が自動清掃を開始する、**Then** ロボットは自律的な走行と清掃を開始する。
2. **Given** 自動清掃が進行中、**When** まだ未清掃の到達可能エリアが残っている、**Then** ロボットは既清掃エリアより未清掃エリアを優先して清掃を継続する。
3. **Given** 清掃対象の到達可能エリアをすべて処理した、**When** セッション終了条件を満たす、**Then** ロボットは移動と清掃を停止し、完了状態を記録する。

---

### User Story 2 - 清掃を一時停止・再開・停止する (Priority: P1)

利用者として、自動清掃中でも状況に応じて一時停止・再開・停止を行いたい。これにより、人の移動や家具の配置変更があっても柔軟に運用できる。

**Why this priority**: 自律動作中に利用者が介入できないと、家庭内での実運用に耐えないため。

**Independent Test**: 自動清掃中に一時停止・再開・停止を順に実施し、ロボットが直ちに反応し、再開時には残りの清掃を継続できることを確認する。

**Acceptance Scenarios**:

1. **Given** ロボットが自動清掃中、**When** 利用者が一時停止を指示する、**Then** ロボットは移動と清掃を停止し、進捗を保持したまま一時停止状態になる。
2. **Given** ロボットが一時停止状態、**When** 利用者が再開を指示する、**Then** ロボットは保持していた進捗に基づいて未清掃エリアの清掃を再開する。
3. **Given** ロボットが自動清掃中または一時停止中、**When** 利用者が停止を指示する、**Then** セッションは終了し、終了理由が利用者停止として記録される。
4. **Given** ロボットが自動清掃中・一時停止中・ドック復帰中のいずれか、**When** 利用者またはシステムがe-stopを発行する、**Then** ロボットは50ms以内に移動と清掃を停止し、安全停止状態へ遷移する。

---

### User Story 3 - 中断が起きても残りの掃除を続ける (Priority: P2)

利用者として、一部の場所に行けなくなっても掃除全体がすぐ失敗せず、掃除できる範囲は続けてほしい。これにより、閉じたドアや一時的な障害物があっても清掃成果を最大化できる。

**Why this priority**: 家庭環境では一時的な通行不可が起きやすく、全体停止だけでは実用性が低いため。

**Independent Test**: 清掃中に一部の通路を塞ぎ、ロボットが他の到達可能エリアの清掃を継続し、最後に未実施エリアを理由付きで報告することを確認する。

**Acceptance Scenarios**:

1. **Given** 自動清掃中に一部エリアへの経路が一時的または継続的に失われた、**When** 他に到達可能な未清掃エリアが存在する、**Then** ロボットは清掃可能な他エリアの清掃を継続する。
2. **Given** 清掃継続に必要な現在位置把握または移動継続が成立しない、**When** 自動復旧を試みても継続不能と判断される、**Then** ロボットは安全に停止し、未完了として終了理由を記録する。

---

### User Story 4 - 清掃結果を確認する (Priority: P3)

利用者として、自動清掃が完了したのか、途中で止まったのか、どこまで掃除できたのかを知りたい。これにより、次に手動介入が必要かどうかをすぐ判断できる。

**Why this priority**: 清掃そのものより優先度は下がるが、運用上の判断に必要な最低限の可視性がないと再利用しづらいため。

**Independent Test**: 正常完了・利用者停止・未完了終了の各パターンを発生させ、各セッションで状態・進捗・未実施理由が確認できることを検証する。

**Acceptance Scenarios**:

1. **Given** 自動清掃セッションが終了した、**When** 利用者が結果を確認する、**Then** 完了状態、清掃進捗、未実施エリアの有無、および終了理由が確認できる。

### Edge Cases

- 清掃開始要求時に、利用可能な室内地図または現在位置がない場合は開始を拒否し、理由を返す。
- 清掃開始要求時に、バッテリー残量が30%未満の場合は開始を拒否する。
- 清掃中に低バッテリーを検知した場合は、ドック復帰を試み、復帰できない場合は未完了で安全停止する。
- 清掃対象の一部が閉じたドアや移動した家具で到達不能になった場合は、他の到達可能エリアを清掃し、到達不能エリアを未実施として記録する。
- 一時停止中に再度一時停止が要求された場合は、状態を変えずに現在の一時停止状態を維持する。
- 清掃中に利用者が停止を指示した場合は、途中までの進捗を失わずに終了結果へ反映する。
- 自動復旧を試みても継続不能な場合は、その場で清掃を終えるのではなく、終了理由を明示した未完了結果を残す。
- 清掃中にe-stopが発行された場合は、実行フェーズに関係なく50ms以内に駆動系と清掃系を停止し、明示解除まで再開しない。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: システムは、待機状態のロボットに対して自動清掃セッションを開始できなければならない。
- **FR-002**: システムは、自動清掃開始前に、清掃対象の室内地図、現在位置、バッテリー残量が**30%以上**であることを確認し、条件を満たさない場合は開始を拒否し理由を示さなければならない。
- **FR-003**: システムは、自動清掃の対象を、毎回、地図上で清掃可能かつ到達可能な全床面から、禁止領域および清掃対象外領域を除いた範囲として扱わなければならない。禁止領域は、Nav2 の keepout レイヤーまたはパラメータ経由で提供される前提とする。
- **FR-004**: システムは、自動清掃セッション中、対象範囲を自律的に走行しながら清掃を実行しなければならない。
- **FR-005**: システムは、セッション進行中、既清掃エリアと未清掃エリアを区別し、未清掃かつ到達可能なエリアを優先して清掃しなければならない。
- **FR-006**: システムは、現在セッションにおける各エリアの状態を、少なくとも「清掃済み」「未清掃」「未実施」で識別できなければならない。
- **FR-007**: 利用者は、自動清掃セッションを一時停止、再開、停止できなければならない。
- **FR-008**: システムは、一時停止指示を受けた場合、移動と清掃を停止し、セッション進捗を保持したまま一時停止状態へ遷移しなければならない。
- **FR-009**: システムは、再開指示を受けた場合、保持していた進捗に基づいて未清掃エリアの処理を再開しなければならない。
- **FR-010**: システムは、停止指示を受けた場合、セッションを終了し、終了理由を「利用者停止」として記録しなければならない。
- **FR-011**: システムは、現在位置の把握不足、経路喪失、または残りエリアへの継続的な到達失敗など、清掃継続不能な状態を検知できなければならない。
- **FR-012**: システムは、FR-011を検知した場合、**1回**の自動復旧（AMCL による再ローカライズ試行または代替経路の再計画）を試み（最大**30秒**）、それでも継続不能な場合は未完了として終了しなければならない。
- **FR-013**: システムは、一部エリアのみが到達不能になった場合でも、他に到達可能な未清掃エリアがある限り、清掃全体を即時終了してはならない。
- **FR-014**: システムは、自動清掃セッションの状態語彙を `idle(待機)` `preparing(準備中)` `cleaning(清掃中)` `paused(一時停止)` `docking(ドック復帰中)` `safety_stopped(安全停止)` `completed(完了)` `incomplete(未完了)` に正規化し、外部から確認可能にしなければならない。
- **FR-015**: システムは、セッション終了時に、完了状態、清掃進捗、未実施エリアの有無、および終了理由を利用者が確認できる形で残さなければならない。
- **FR-016**: システムは、対象範囲の到達可能エリアをすべて処理した場合、移動と清掃を停止して完了状態へ遷移しなければならない。
- **FR-017**: システムは、清掃中にバッテリー残量が**20%未満**となった場合、清掃継続よりドック復帰の試行を優先しなければならない。
- **FR-018**: システムは、FR-017のドック復帰が成功した場合、そのセッションを低バッテリー終了として終了しなければならない。
- **FR-019**: システムは、FR-017のドック復帰が失敗した場合、現在位置で安全停止し、未完了として終了理由を記録しなければならない。
- **FR-020**: システムは、運用中の任意フェーズでe-stop要求を受け付けなければならない。
- **FR-021**: システムは、FR-020のe-stop要求受信後、**50ms以内（1制御周期以内）**に移動および清掃アクチュエータを停止しなければならない。
- **FR-022**: システムは、e-stop発動後、明示的な解除操作があるまで清掃再開を許可してはならない。
- **FR-023**: システムは、自律走行中の障害物回避判定において、LiDAR・RGBカメラ・RGBDカメラ由来の障害物情報を統合して利用しなければならない。
- **FR-024**: システムは、`/autonomous_cleaning/clear_estop` インターフェースを提供し、e-stop解除は「ロボットが停止している」「アクティブな安全故障がない」の両条件を満たす場合にのみ成功させなければならない。
- **FR-025**: システムは、`/diagnostics` に自ノードの状態を公開し、少なくとも `session_state` `localization_health` `battery_charge_ratio` `dock_attempt_state` `estop_latched` を含めなければならない。

### Key Entities *(include if feature involves data)*

- **AutonomousCleaningSession**: 1回の自動掃除実行を表す単位。開始時刻、終了時刻、状態、終了理由、進捗要約を持つ。
- **CleaningArea**: 清掃対象として扱う空間区画。到達可否、禁止可否、清掃状態を持つ。
- **CoverageState**: セッション中の進捗情報。清掃済み割合、残エリア、未実施エリアを持つ。
- **InterruptionRecord**: 継続不能または一時的な中断を表す記録。発生理由、影響範囲、復旧結果を持つ。
- **SessionState**: 自動清掃セッションの正規状態集合。`idle/preparing/cleaning/paused/docking/safety_stopped/completed/incomplete` を取り、外部公開と内部遷移の単一語彙として扱う。
- **EStopState**: e-stopのラッチ状態と解除可否判定を表す。`latched`/`cleared` と、解除拒否理由を持つ。
- **PerceptionFusionHealth**: LiDAR・RGB・RGBDの障害物情報統合の健全性を監視する。`healthy/degraded/lost` 状態を持つ。
- **DiagnosticsSnapshot**: `/diagnostics` へ公開する必須キー（`session_state`, `localization_health`, `battery_charge_ratio`, `dock_attempt_state`, `estop_latched`）のスナップショット。

## Assumptions

- 本機能は、事前に利用可能な室内地図が存在する環境で使う前提とする。
- 清掃対象は、毎回、地図上で清掃可能かつ到達可能な全床面とし、部屋単位やゾーン単位の選択は本機能の対象外とする。
- 段差、ケーブル、カーペット種別、動的障害物の詳細認識と回避は別機能で扱い、本仕様では清掃対象として扱える領域が事前または実行時に判定済みである前提とする。
- 通常の完了時または利用者停止時の自動充電復帰は本機能の対象外とし、終了時は現在の安全な停止位置で完了または未完了となる。
- 清掃中の低バッテリー時のみ、例外的にドック復帰を試みる。
- バッテリー閾値は、開始可否判定を30%以上、低バッテリー判定を20%未満とする。
- 自動復旧は1回・最大30秒とし、失敗時は未完了終了へ遷移する。
- e-stop発動時は50ms以内に停止し、明示解除まで再開しない。
- e-stop解除要求時に「停止未達」または「安全故障あり」の場合は、解除を拒否して安全停止状態を維持する。
- 閉じたドアや家具移動などで一時的に行けない場所は、そのセッションでは未実施エリアとして扱う。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 開始条件を満たす環境では、利用者が自動清掃を開始してから10秒以内に「清掃中」状態へ遷移できる。
- **SC-002**: 標準的な家具配置の室内検証で、1回の自動清掃セッションにより到達可能な清掃対象床面の90%以上を処理できる。
- **SC-003**: 一時停止または停止の指示に対して、95%以上の試行で2秒以内に移動と清掃が止まる。
- **SC-004**: 一時的な経路喪失または位置把握不良が発生した場合、95%以上の試行で30秒以内に清掃再開または未完了終了のいずれかへ明確に遷移する。
- **SC-005**: セッション終了後10秒以内に、利用者が完了状態、清掃進捗、未実施エリアの有無、終了理由を確認できる。
- **SC-006**: 一部エリアが途中で到達不能になる検証条件でも、残る到達可能エリアの清掃継続率が90%以上である。
- **SC-007**: 清掃中の低バッテリー検知時、95%以上の試行で60秒以内にドック復帰開始または未完了停止のいずれかへ遷移する。
- **SC-008**: e-stop要求に対して、全試行で**50ms以内**に移動と掃除が停止する。
- **SC-009**: `/diagnostics` には1秒以内の更新間隔で `session_state` `localization_health` `battery_charge_ratio` `dock_attempt_state` `estop_latched` が反映される。
- **SC-010**: e-stop解除要求に対して、前提条件を満たす試行では95%以上で解除成功し、前提条件を満たさない試行では100%解除拒否となる。
